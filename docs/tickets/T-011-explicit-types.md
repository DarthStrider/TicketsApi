# T-011 Explicit types instead of `var` (chore)

**As a** developer, **I want** the existing code to use explicit types and the build to reject a new `var` **so that** the whole codebase follows design principle 2 (`docs/design-principles.md`) and nobody has to check it by hand in reviews.

This is a pure refactor. Clients see no change, and no behaviour changes.

## Acceptance criteria

### Conversion
1. Given any `.cs` file under `src/` or `tests/` (except the generated migrations in criterion 2), when I search it for `var` declarations, then each one has been replaced with its explicit type, or with target-typed `new()` when the type is already written on the left (`List<Ticket> tickets = new();`, `JsonSerializerOptions options = new() { ... };`).
   - This covers every form of `var`: local declarations, `using var`, `foreach (var ...)`, `out var ...` and deconstruction (`var (a, b) = ...` becomes `(int a, string b) = ...` or `(int a, string b)` declared explicitly).
   - **The only exception** is a variable of an anonymous type (`var payload = new { title = "t" };`, or a LINQ projection to an anonymous type). It stays `var`, because the type has no name.
   - Nullable annotations are kept exact: a `var` that held a `Ticket?` becomes `Ticket?`, not `Ticket` with a `!`.
2. The generated EF Core migration files in `src/TicketsApi/Data/Migrations/` are not changed by this ticket, and they are excluded from the enforcement in criterion 3.
   - `.editorconfig` has a section for that folder (`[src/TicketsApi/Data/Migrations/**.cs]`) with `generated_code = true`. This is needed because `20261123153609_InitialCreate.cs` has no `// <auto-generated />` header, so the analyzers would otherwise check it. Future migrations generated by `dotnet ef migrations add` are covered by the same section.

### Enforcement
3. A root `.editorconfig` (with `root = true`) is added. For `*.cs` it sets:
   - `csharp_style_var_for_built_in_types = false:warning`
   - `csharp_style_var_when_type_is_apparent = false:warning`
   - `csharp_style_var_elsewhere = false:warning`
   - `dotnet_diagnostic.IDE0008.severity = warning` (IDE0008 is "use explicit type instead of `var`"; the explicit diagnostic setting makes sure the command-line build uses this severity, not only the IDE).
4. `Directory.Build.props` sets `<EnforceCodeStyleInBuild>true</EnforceCodeStyleInBuild>`, so the code-style rules run during `dotnet build`. It is set only there, not in any `.csproj`.
   - `Directory.Build.props` already sets `<TreatWarningsAsErrors>true</TreatWarningsAsErrors>`. That means the IDE0008 warning becomes an **error**: a stray `var` with a named type fails `dotnet build`, locally, in the commit hook and in CI.
5. Given the finished change, when a developer temporarily adds `var count = 0;` to a file in `src/` and to a file in `tests/`, then `dotnet build` fails with IDE0008 naming each file and line. Given the same line added to a file in `src/TicketsApi/Data/Migrations/`, then the build does not fail. Given `var payload = new { title = "t" };`, then the build does not fail. The developer shows this output in the PR description and removes the temporary lines (none of them is committed).

### Pure refactor
6. No behaviour changes. The only changes are: `var` replaced in `.cs` files under `src/` and `tests/`, the new `.editorconfig`, and the one property in `Directory.Build.props`. No other code, configuration, package or migration file changes.
7. No test is deleted, skipped or weakened, and no assertion changes. Given the test count from `dotnet test` on `main` before the change, when `dotnet test` runs after the change, then the same number of tests run and all of them pass. Both counts are shown in the PR description.
8. `dotnet build` passes with 0 warnings and 0 errors, and `dotnet test` passes.

### Format and CI
9. Given the finished change, when `dotnet format --verify-no-changes` runs, then it exits with code 0 and changes no file. (CI runs this same command as its "Format check" step.)
10. CI passes on the pull request. CI builds with the same `Directory.Build.props` and `.editorconfig`, so a stray `var` fails CI the same way it fails a local build (criterion 4).

## Out of scope
- Any other style rule in `.editorconfig` beyond the three `var` options and IDE0008 (for example naming rules, `csharp_style_implicit_object_creation_when_type_is_apparent` / IDE0090 for `new()`, expression-bodied members, `using` placement, indentation). Target-typed `new()` is used in the conversion (criterion 1) but is not enforced by the build.
- Changes to the CI workflow (`.github/workflows/ci.yml`). The existing steps (restore, format check, build, test) already cover this ticket.
- Changes to the generated migrations in `src/TicketsApi/Data/Migrations/`.
- Any other cleanup found while converting (renames, comments, refactors). Suggest it as a new ticket instead.
